Inside this text document I talk about every technical choice I made when making this game.

My game is composed of two unity scenes and 10 scripts in c#.

These 10 scripts include:


Two different kinds of enemy movement. one for making the enemy move left and right, and the other script I had made for a bouncy ball enemy I made.

The normal enemy movement is EnemyMovement.cs which takes in a transform (or a specific point in the game) to be used as the start position for the enemy, along with two floats (numbers that can have Decimal units) one for the distance that the enemy will move from the start position and the second Float number is for the enemy's Speed. This is used to change how fast or slow the Enemy moves back and forth from its start position.
It works is by using "mathf.PingPong" to make an offset for the enemy which is then used to change the enemies position.

(as a note: a mistake I noticed here is how I should have used "Time.Fixedtime" instead of just "Time.time" since I put the "Mathf.PingPong" inside of "FixedUpdate". 
I don’t quite understand what the difference between these methods actually are or what using them like this entails.
Though I personally didn’t see any problem with how the game was running. 
But I will need to remind myself to not make similar mistakes in later projects.)

For the second enemy movement script, BouncyEnemyMovement.cs takes the ground check used by PlayerController.cs in four directions to see if they have hit a wall/roof or not. 

To put it simply: every frame Physics2D.OverlapCircle is used to check if the bouncy Enemy has hit a wall on either to the left, right, up, or down. 
Then if they find that the bouncy ball has hit one of these sides, then the bool GoLeft gets turned on or off, or the bool GoUpward get turned off or on.
These bools then decide which direction the bouncy Enemy should go by using RigidBody.linearVelocity much like in PlayerController.cs to change their direction.

Notably I did mix up the left and right directions when the bouncy ball is supposed to move but I did fix it by working around it with the consequence that now if the check on the left is triggered, then GoLeft is TURNED ON and if the check on the right is triggered then GoLeft is TURNED OFF.

(Another thing to note: I made the same mistake as in "EnemyMovement.cs" by using Time.deltaTime inside FixedUpdate instead of Time.fixedDeltaTime. Though much like in "EnemyMovement.cs" I didn’t notice that this may be a problem until I realised that there was a version meant to be used in FixedUpdate and that thusly I was probably using the wrong one. Despite those details i am quite happy with how this script works, even though I could have used a physics material to possibly make the exact same bouncy effect.)




Two Scripts affect the players health. and the UI for the Players health.
One of these is Health.cs which is the script in the game which has the players health. it has two variables. MaxHealth. and CurrentHealth. along with two methods SetHealth and TakeDamage.

SetHealth takes in the int "value" and checks if value is larger than MaxHealth before setting CurrentHealth to the new "value" and TakeDamage takes in the int "damage" and checks if it’s larger than zero, if it is, then it will use SetHealth to set the CurrentHealth to the CurrentHealth minus damage.

The second is HealthUI.cs which works by taking in "Health.cs" via "FindWithTag" to get the player as a GameObject to the use ".GetComponent" to extract the Health script from the player.
Then by using a public TextMeshProUGUI object (also known as a text object) to drag in the health text.

These are then used inside a method that takes the current health of the player, converts it into a sting (I.E a series of letters for the computer), then sets the new text to the text of the health display to reflect the player's current health.

Notably this method is the first time I have used the event system in unity and I realised a bit later that this is quite dumb way to use it.
Since instead of needing every enemy call on the same event after the player has taken damage to update the UI I could just have put the trigger for that event inside the health script directly.
If I am to make further changes to the game this will likely be among the first I would do.




There is one script which the enemies use to damage the player which is: PlayerHurterScript.cs which has an int variable for the amount of damage an enemy does and a bool for instantly killing the player. 
It works by taking in Health.cs via GameManager.cs which is gotten by using FindWithTag to get the GameManager which i gave its own unique tag. 

Then inside OnCollisionEnter2D or OnTriggerEnter2D to see if a player has collided/entered this object there is a compareTag to see if the player has collided or not. 
If the player has collided with them, they call upon GameManager.cs to make Health.cs call the damage method with however much damage the enemy has.

(As a note here. Because of how I set up the health script with two methods. one for setting the players health to a number and the other for reducing the players health by a number.
that Means the instant kill version of the player damaging script (Which uses the set health method instead of the deal damage method) totally ignores the deal damage method 
(which I added things like Invulnerability time to so you don’t get obliterated by running though multiple enemies at once) which means you could walk though an enemy then walk into an insta-killing enemy and instantly die)



GameManager.cs is the state machine behind the game. It works by having a public enum with three states. Running, Stopped, and Won. These states are checked inside two if statements inside the GameManagers default unity update method these if statements check two simple things. IS the player alive? Which it does by having Health.cs (Which was dropped in via the unity editor along with the PlayerRespawnHandler.cs) 
If the player's health dips to 0 while the GameState is "running" then it calls upon the StartCoroutine PlayerDeath from the "PRH" or "Player Respawn Handler" to activate the gameover screen and turn the game state to "stopped" to stop the corutine from being invoked every frame.
If the enum "GameState" becomes "won" it does nearly the exact same thing. Expect the PlayerRespawnHandler turns on the WinScreen before setting the GameState to Stopped.



PlayerRespawnHandler.cs is a rather simple script/klass. It has three corutines, which are: "PlayerDeath", "Win" and "StartGame".
"PlayerDeath" and "Win" do nearly the exact same thing. they turn off the player controller, the HealthUI, change the GameManager's GameState to "Stopped", change the timescale to 0, and then turn on either the win or gameover screen depending on which corutine was triggered while turning off the other.

"StartGame" just does the opposite, Triggered by void start inside the GameManager, it sets the GameState to "Running", sets the time scale to 1, and turns off any gameover/WinScreen while turning on the HealthUI



MenuManager.cs is a class that only has three methods. and is also what’s used in every menu in the game. namely these methods are:

StartGame which just loads the GameScene using the unity sceneManager and since i didnt touch since i started this project, and thus needs to be feed the name of the GameScene inside the unity editor.
MenuButton, which just loads the menu scene, without needing any input via the unity editor and the Quitbutton. Which uses Application.Quit(); to turn off the game. Though an error that did pop up was when renaming this method did break the quit button in the main menu since it was trying to refer to a method that no longer existed, but i have since fixed that bug.



The winpad script: this is perhaps the simplest script in the game. All it does is check if the player has collided with it using the same method that PlayerHurterScript.cs uses
and then changes the GameState inside GameManager to "won" to end the game.



PlayerController.cs is the script responsable for player movement. With two public floats for the players speed and jump height, the player movement is divided between the method Jump inside update, and "Move" inside fixed update.

Move uses RigidBody.linearVelocity to change the linearVelocity along the x axis. and using a float inside the update funtion to see if the player is meant to move forwards or backwards by using "Input.GetAxisRaw("Horizontal");" inside movement I also added two if statements to see if "Input.GetAxisRaw("Horizontal");" was positive or negate to then flip the player sprite accordingly.

Physics2D.OverlapCircle is used to see if the player is on valid ground, and if they are then the players Linear y Velocity will be set to the jumpheight making the player jump
also of note is how att the start of the jump method is a check to see if the input is spacebar, and if it isnt then nothing else happens in the program.
